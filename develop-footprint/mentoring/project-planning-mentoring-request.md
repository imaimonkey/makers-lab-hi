## 1. 현 단계 구성 내용 및 상태

### 1.1 프로젝트가 만들고 있는 것

이 프로젝트는 현대해상 신규위험 탐색 실무자가 다음 흐름을 한 작업 공간에서 이어가도록 하는 제품 프레임이다.

```text
외부·내부 신호 확인
  → 위험 후보 정리
  → 근거·반증·상품화 가능성 평가
  → 진행/보류/종료 결정
  → 검토용 리포트
```

고객의 생활 상황과 영업부서의 현장 관찰을 별도 입력 경로로 받아, 개인정보를 포함한 원문을 분석가 후보 데이터로 직접 넘기지 않고 비식별·집계된 연구 신호로 연결하는 방향도 함께 설계되어 있다.

### 1.2 현재 화면과 구현 상태

| 영역 | 사용자와 목적 | 현재 상태 | 아직 없는 것 |
| --- | --- | --- | --- |
| `/` | 신규위험 신호·후보·고객 인사이트를 보는 실무자 대시보드 | UI 구현, 샘플 표시 | 실제 수집 API, 후보 저장소, 운영 최신성·장애 처리 |
| `/risks` | 위험 후보 검색·필터·상태 확인 | UI 구현, 샘플 표시 | 후보 CRUD, 중복 병합, 담당자·권한·감사 이력 |
| `/risks/:riskId` | 위험 정의, 근거, 반증, 기존 상품 비교, 상품화 평가 | UI 구현, 샘플 표시 | 실제 근거 계보, 상품·약관 검색, 평가 저장·승인 |
| `/reports` | 의사결정용 종합 리포트 작성·검토·내보내기 | UI 구현, 일부 로컬/샘플 흐름 | 운영 저장소, 역할별 승인, 접근권한 있는 내보내기 |
| `/customer-insight` | 개인 고객의 상황 탐색과 선택적 연구 신호 공유 | UI 구현, 로컬 동작 | 고객 인증, 서버 비식별화, 동의 원장, 집계 API |
| `/sales-intake` | 영업부서의 현장 리포트·상품개발 제안 접수 | UI 구현, 로컬 동작 | SSO·RBAC, 접수 API, 담당자 배정, 후보 연결 |

상태 용어는 다음처럼 사용한다.

- `UI 구현`: 화면과 상호작용이 만들어져 있음
- `로컬 동작`: 브라우저 내부 상태로 흐름을 시연할 수 있음
- `샘플 표시`: 가상 데이터이며 실제 업무 판단에 사용할 수 없음
- `미연동`: 인증·API·데이터 저장·운영 절차가 연결되지 않음

### 1.3 현재까지 합의해 둔 설계 원칙

- 신호, 위험 후보, 상품 개발 과제, 리포트를 서로 다른 엔터티로 둔다.
- 신호 강도, 근거 신뢰도, 손실 명확성, 상품화 적합성을 하나의 점수로 숨기지 않는다.
- 모든 판단에 근거 ID, 최신 시각, 불확실성, 반증 또는 보류 이유를 남긴다.
- 고객 이름·연락처·주민등록번호·상세 주소·자유입력 원문을 분석가 후보 데이터에 저장하지 않는다.
- 고객 한 건의 신호를 신규위험 후보로 자동 승격하지 않고, 최소 집계·중복 확인·사람의 검토를 거친다.
- 상품 보장·면책·보험료·가입 가능 여부를 앱이 확정하지 않고 공식 문서와 확인 필요 항목으로 연결한다.
- 고객 채널은 `CustomerLayout`, 실무자 채널은 `RootLayout`, 영업부서 입력은 `SalesLayout`으로 분리한다.

### 1.4 현재 상태에 대한 자체 판단

현재 결과물은 운영 서비스가 아니라, 문제 공간과 화면 간 연결을 검토하기 위한 프로토타입이다. 안정 라우트와 핵심 사용자 흐름은 구성되어 있지만, 실제 업무의 우선순위·승인 게이트·담당 조직·데이터 가용성·성공 기준은 아직 멘토와 현업 검증이 필요한 상태다.

따라서 이번 멘토링에서는 화면을 더 추가하는 것보다 다음을 결정하는 데 초점을 두고 싶다.

1. 누구의 어떤 결정을 가장 먼저 개선할 것인가?
2. 첫 운영 파일럿에서 반드시 살아 있어야 하는 흐름은 어디까지인가?
3. 어떤 기능·데이터·통합은 후순위로 미뤄도 되는가?
4. 어떤 기준으로 프로토타입에서 운영 개발로 넘어갈 것인가?

## 2. 이번 멘토링에서 확인받고 싶은 결론

멘토링 종료 시 아래 다섯 가지를 문장과 표로 남길 수 있으면 좋겠다.

| 확인할 결론 | 원하는 형태 |
| --- | --- |
| 핵심 문제와 1차 사용자 | 한 문장 문제 정의와 우선 사용자 1개 또는 2개 |
| MVP 범위 | 반드시 포함할 흐름, 제외할 흐름, 샘플로 남길 흐름 |
| 운영 업무 모델 | 입력자·분석가·검토자·관리자의 책임과 인계 지점 |
| 개발 우선순위 | 다음 2~3개 개발 슬라이스와 선행 의존성 |
| 검증 방법 | 인터뷰·파일럿·성과 지표·중단/수정 기준 |

## 3. 멘토링 요청 항목

### 3.1 문제 정의와 제품 포지셔닝

1. 이 서비스의 핵심 가치는 `신규위험을 빨리 발견하는 도구`, `신호부터 리포트까지의 협업 워크플로`, `고객·영업 현장의 미충족 위험 환류` 중 무엇으로 설명하는 것이 가장 명확한가?
2. 현재처럼 실무자·개인 고객·영업부서 세 경로를 함께 제시하는 것이 제품 이해를 돕는가, 아니면 1차 릴리스의 초점을 흐리는가?
3. 가장 먼저 개선해야 할 의사결정은 `무엇을 조사할지`, `후보로 올릴지`, `상품화 검토로 넘길지`, `리포트로 승인받을지` 중 무엇인가?
4. 사용자가 이 도구가 없을 때 겪는 비용을 시간, 누락 위험, 중복 조사, 근거 추적 비용 중 무엇으로 정의해야 하는가?

### 3.2 MVP와 범위 조정

1. 첫 운영 파일럿에서는 대시보드·후보 목록·상세 평가·리포트 중 어느 조합만 있어도 가치가 입증되는가?
2. 실제 데이터 연동의 우선순위는 근거 수집, 후보 저장소, 상품·약관 문서, SSO·권한, 리포트 승인 중 무엇인가?
3. 현재 고객 인사이트와 영업부서 접수는 핵심 MVP에 포함해야 하는가, 아니면 실무자 워크플로가 검증된 뒤 연결해야 하는가?
4. `샘플 표시`로 남겨도 되는 영역과 운영 전환 전에 반드시 실제 데이터로 바꿔야 하는 영역을 구분해 달라.
5. 지금 단계에서 삭제하거나 과감히 축소할 기능이 있는가?

### 3.3 업무 흐름과 도메인 경계

1. `신호 → 위험 후보 → 평가 → 리포트`를 별도 단계로 나눈 것이 실제 책임과 잘 맞는가?
2. 신호가 후보가 되는 최소 게이트와, 후보가 상품 개발 검토로 넘어가는 게이트를 각각 어떻게 정의해야 하는가?
3. `진행/보류/종료` 외에 실제로 필요한 상태가 있는가? 상태 변경에 반드시 필요한 입력과 승인자는 누구인가?
4. 근거, 반증, 불확실성, 기존 상품 비교를 같은 상세 화면에 둘 때의 적정 순서와 깊이는 어느 정도인가?
5. 리포트는 앞 단계의 결과를 복사하는 문서인가, 승인 시점의 스냅샷인가, 협업·질문을 남기는 작업 공간인가?

### 3.4 운영 모델과 책임

1. 신호 수집, 후보 정리, 상품화 평가, 리포트 승인, 데이터 보호 검토를 어떤 조직 또는 역할이 맡는 것이 현실적인가?
2. 고객·영업부서 유입 신호를 검토 큐에 넣기 전에 필요한 최소 검토자는 누구인가?
3. 자동화해도 되는 작업과 반드시 사람이 승인해야 하는 작업을 구분해 달라.
4. 근거 삭제, 후보 병합, 상태 결정, 리포트 내보내기에 필요한 권한과 감사 기록 수준은 어느 정도인가?
5. 이 서비스의 운영 책임자가 부재할 때 가장 먼저 발생할 실패는 무엇이며, 제품에서 어떻게 드러내야 하는가?

### 3.5 성공 기준과 검증 계획

1. 초기 파일럿에서 측정할 수 있는 현실적인 지표는 후보 분류 시간, 중복 조사 감소, 근거 완결성, 재검토 준수율 중 무엇인가?
2. 단순히 화면을 사용했다는 사실과 실제 의사결정에 도움이 되었다는 사실을 어떻게 구분할 것인가?
3. 어떤 과거 사례 또는 익명화된 사례를 재현하면 제품 가치를 가장 빨리 검증할 수 있는가?
4. 파일럿 전에 반드시 확인할 가설과, 틀렸을 때 범위를 수정해야 하는 가설은 무엇인가?
5. 멘토가 보기에 이 프로젝트가 중단·피벗되어야 하는 신호는 무엇인가?

### 3.6 다음 개발 순서

현재 로드맵은 근거 수집·출처 계보 → 후보 저장소·목록 → 대시보드·상세 평가 → 리포트 → 고객 신호 운영화 순서로 제안되어 있다. 이 순서가 실제 위험과 의존성을 반영하는지 확인받고 싶다.

1. 위 순서에서 먼저 바꿔야 할 단계가 있는가?
2. 병렬 개발해도 계약 충돌이 적은 작업과 반드시 선행되어야 하는 작업은 무엇인가?
3. 현재 `src/domain` 계약을 먼저 안정화하는 접근이 적절한가, 아니면 업무 시나리오를 더 검증한 뒤 계약을 확정해야 하는가?
4. 다음 멘토링 전까지 완료할 가장 작은 세로 슬라이스를 하나만 고른다면 무엇인가?

## 4. 멘토에게 요청할 피드백 형식

각 항목을 아래 중 하나로 표시해 주시면 다음 개발 결정에 바로 반영하기 좋다.

| 표시 | 의미 |
| --- | --- |
| 유지 | 현재 방향과 범위를 유지 |
| 수정 | 목적은 유지하되 사용자·흐름·계약을 수정 |
| 보류 | 운영 전환 또는 후속 단계로 미룸 |
| 삭제 | 현재 프로젝트 범위에서 제외 |
| 확인 필요 | 현업 또는 법무·준법·데이터 담당 확인 후 결정 |

가능하면 다음 다섯 칸으로 의견을 남겨 주시면 좋다.

```text
대상 항목 | 판단(유지/수정/보류/삭제/확인 필요) | 이유 | 먼저 확인할 사람·자료 | 다음 행동
```
