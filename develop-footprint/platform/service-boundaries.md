# 서비스 경계와 안전 기준

## 운영 배포 경계

현재는 검토 편의를 위해 한 SPA지만 운영에서는 다음 경계를 권장한다.

```text
고객 채널                         실무자 채널
공개 웹/앱                        사내 웹
고객 인증·동의                    SSO·RBAC
     │                               │
Customer Guidance API          Risk Workbench API
     │                               │
승인 상품·문서 서비스           근거·후보·평가·리포트 저장소
     └─ Emerging Signal Intake ─ 집계·검토 큐
```

고객 API와 사내 API는 인증, 네트워크, 데이터 저장소, 감사 정책을 분리한다. 고객 입력을 분석가 브라우저가 직접 조회하는 구조는 허용하지 않는다.

영업부서 리포트 입력은 고객 원문을 전달하는 통로가 아니라, 영업 담당자가 비식별 맥락을 요약해 제출하는 별도 `Sales Signal Intake API` 경계로 둔다. 접수 데이터는 SSO·RBAC와 감사 로그를 적용하고, 위험 후보 큐로 보내기 전에 중복·최소 집계·사람 검토를 거친다. 현재 `/sales-intake`는 이 경계를 시연하는 내부 업무형 로컬 프레임이며 운영 API가 아니다.

## 개인정보와 동의

- 목적에 필요한 최소 입력만 수집한다.
- 연구 신호 공유는 상품 탐색과 분리된 선택 동의다.
- 동의 문구 버전, 시각, 목적, 철회와 삭제 이력을 관리한다.
- 클라이언트 마스킹은 보조 수단이다. 서버에서 재검사하고 원문 보존을 최소화한다.
- 실무자에게는 최소 집계 기준을 통과한 범주, 추세, 갭 가설만 제공한다.
- 희귀 조합, 자유서술 인용, 위치·직업 세부값으로 재식별되지 않는지 검토한다.

구체적인 보존기간과 집계 임계값은 개인정보보호·준법 담당자의 승인을 받아야 하며 이 프로토타입에서 임의로 정하지 않는다.

## 추천과 계약

상품 후보 제시는 다음 단계와 분리한다.

1. 관련 가능성이 있는 상품 탐색
2. 최신 약관·상품설명서·판매 상태 확인
3. 고객 정보 확인과 적합성·적정성 절차
4. 보험료 계산과 인수 심사
5. 고객의 명시적 확인과 공식 계약

앱은 1단계 탐색 프로토타입만 수행한다. 외부 공식 링크로 이동했다고 계약이 시작되거나 정보가 자동 이전되었다고 표현하지 않는다.

## AI·검색·수집 서비스

- 생성형 요약은 원문 URL, 수집 시각, 발행 시각, 발췌 범위를 보존한다.
- 검색 결과 부재를 보장 부재로 해석하지 않는다.
- 프롬프트나 모델 출력에 고객 식별정보를 넣지 않는다.
- 모델·프롬프트·검색 인덱스 버전을 판단 기록과 연결한다.
- 환각, 출처 중복, 오래된 약관, 악성 문서 삽입을 탐지하는 검토 단계를 둔다.
- 자동 점수는 우선순위 보조이며 상품 개발·거절 결정을 단독 수행하지 않는다.

## 인증·권한·감사

운영 사내 앱은 SSO와 역할 기반 권한을 사용한다. 최소 역할 예시는 관찰자, 분석가, 검토자, 관리자다. 영업부서 리포트에는 입력자와 검토 담당을 구분하고, 상태 결정, 근거 삭제, 후보 병합, 보고서 내보내기는 행위자·시각·이전값·새값·사유를 감사 로그에 남긴다.

프런트엔드에서 버튼을 숨기는 것만으로 권한을 보장하지 않는다. 모든 쓰기 권한은 API에서 다시 검사한다.

## 장애와 품질

- 일부 소스 실패를 전체 데이터 0건으로 표시하지 않는다.
- 마지막 정상 데이터와 현재 지연 시간을 구분한다.
- 추천·분석 API 실패 시 추정 결과를 조용히 대신 보여주지 않는다.
- 데이터 계약 변경은 스키마 버전과 하위 호환 기간을 둔다.
- 고객·실무자 채널 모두 요청 ID를 제공해 지원과 감사를 가능하게 한다.
