## 1. 현 단계 구성 내용 및 상태

### 1.1 서비스가 가정하는 업무 흐름

현재 서비스는 보험상품 개발 실무자가 신호를 확인한 뒤, 위험 후보를 정리하고, 근거와 기존 상품을 비교해 상품화 가능성을 평가하고, 검토용 리포트로 공유하는 흐름을 가정한다.

```text
신호 확인
  → 후보 정리
  → 손실사건·노출집단 정의
  → 근거·반증·기존 상품 비교
  → 상품화 가능성 평가
  → 진행/보류/종료
  → 리포트·다음 조사 과제
```

추가로 개인 고객의 상황 입력과 영업부서의 현장 리포트를 별도 경로로 받아, 반복되는 미충족 위험을 연구 신호로 검토하는 구조를 구성했다.

### 1.2 현재 화면에서 제공하려는 정보

| 화면 | 실무자에게 보여주려는 내용 | 현재 상태 |
| --- | --- | --- |
| `/` 신규위험 대시보드 | 최근 변화, 소스 상태, 검토가 필요한 후보, 집계된 고객 신호 | UI 구현, 샘플 표시 |
| `/risks` 위험 후보 목록 | 후보 검색·필터·정렬, 상태·담당자·다음 검토일 | UI 구현, 샘플 표시 |
| `/risks/:riskId` 위험 상세 | 한 문장 위험 정의, 추세, 근거 원장, 반증, 기존 상품 비교, 상품화 평가 | UI 구현, 샘플 표시 |
| `/reports` 종합 리포트 | 위험·손실 시나리오·근거·상품 가설·미결 질문·결정 정리 | UI 구현, 로컬/샘플 흐름 |
| `/customer-insight` 고객 인사이트 | 고객 상황에 대한 상품 탐색과 선택 동의된 비식별 연구 신호 | UI 구현, 로컬 동작 |
| `/sales-intake` 영업부서 현장 리포트 | 영업 현장의 반복 문의·위험 관찰·상품개발 제안 접수 | UI 구현, 로컬 동작 |

### 1.3 현재 구현과 운영 상태의 구분

현재 1~4번 실무자 화면은 주로 구조 검토용 샘플 데이터다. 고객 인사이트와 영업부서 입력은 브라우저 `localStorage`를 사용하는 로컬 프로토타입이며, 다음 운영 요소는 아직 연결하지 않았다.

- 실제 신호 수집·근거 계보·위험 후보 저장 API
- 현대해상 사내 인증, 역할 기반 권한, 담당자 배정
- 승인된 상품 마스터·약관·상품설명서와의 최신 문서 연계
- 상품·보장·면책·보험료·가입 가능 여부를 판단하는 실제 업무 시스템
- 리포트 승인, 상태 이력, 감사 로그, 운영 알림
- 고객 동의 원장, 서버 측 개인정보 재검사, 최소 집계·철회·삭제 처리

따라서 현재 화면의 숫자, 후보, 추천, 판단은 실제 현대해상 내부 데이터나 상품 판단을 의미하지 않는다. 상품 정보는 공식 문서 확인이 필요한 탐색용 메타데이터이며, 고객 한 건의 신호가 신규위험 후보로 자동 승격되는 구조도 의도적으로 구현하지 않았다.

### 1.4 실무자에게 확인받아야 하는 미검증 가정

| 가정 | 현재 설계 | 실무 확인이 필요한 부분 |
| --- | --- | --- |
| 신규위험은 신호·후보·평가·리포트의 단계로 관리할 수 있다 | 단계와 상태를 분리함 | 실제 조직의 업무 인계·승인 단계와 일치하는가 |
| 네 가지 평가 축을 따로 보면 판단 근거가 선명해진다 | 신호 강도·근거 신뢰도·손실 명확성·상품화 적합성 | 실무에서 필요한 축과 표현인가, 추가 축이 있는가 |
| 고객·영업 입력은 집계된 연구 신호로 유용하다 | 원문 대신 테마·맥락·갭 가설을 전달 | 실제 조사 우선순위에 도움이 되는 최소 집계 기준은 무엇인가 |
| 근거와 반증을 함께 기록하면 리포트 신뢰도가 높아진다 | 근거 ID·시점·반증·불확실성 기록 | 실제 검토·보고 과정에서 반드시 필요한 필드는 무엇인가 |
| 화면의 다음 조치가 업무를 이어준다 | 담당자·기한·다음 조사 과제 표시 | 누가 어떤 시스템에서 후속 조치를 수행하는가 |

## 2. 이번 멘토링에서 확인받고 싶은 것

이번 대화의 목표는 화면에 대한 일반적인 선호를 묻는 것이 아니라, 실제 업무의 기준과 연결되는지 확인하는 것이다.

1. 실제로 신규위험을 발견하고 검토하는 시작점은 어디인가?
2. 어떤 정보가 모였을 때 “더 조사할 후보”로 볼 수 있는가?
3. 상품화 검토를 진행·보류·종료로 나누는 실무 기준은 무엇인가?
4. 리포트가 의사결정에 쓰이려면 누가, 어떤 형식으로, 어느 정도의 근거를 봐야 하는가?
5. 고객·영업 현장 신호가 실제 업무에 들어올 때 유용한 조건과 위험한 조건은 무엇인가?
6. 이 프로토타입을 한 가지 실제 또는 익명화 사례로 시험한다면 어떤 사례가 적합한가?

## 3. 멘토링 요청 항목

### 3.1 실제 업무 시작점과 신호

1. 최근 신규위험 또는 상품개발 아이디어를 검토하게 된 계기는 무엇이었는가? 예: 사고·보상 데이터, 고객 문의, 영업 현장, 산업 변화, 규제, 경쟁사, 연구자료 등.
2. 현재 그 신호를 어디에서 찾고, 어떤 자료로 정리하며, 누구에게 공유하는가?
3. 기사·검색량·고객 문의·현장 리포트·사고 데이터·규제 변화 중 실제로 신뢰하거나 우선 검토하는 신호는 무엇인가?
4. 같은 사건의 반복 보도나 단일 고객 사례처럼 신호로 보기 어려운 것은 무엇인가?
5. “조사할 가치가 있다”고 판단하려면 최소한 어떤 사실과 출처가 있어야 하는가?
6. 대시보드에서 가장 먼저 보고 싶은 것은 최근 변화, 손실 가능성, 기존 상품과의 관계, 데이터 신뢰도 중 무엇인가?

### 3.2 후보 등록과 평가 기준

1. 후보를 처음 등록할 때 반드시 필요한 정보와 나중에 보완해도 되는 정보를 나눠 달라.
2. 현재 제안한 `위험 정의 → 노출집단 → 손실사건 → 원인 → 손실 유형` 구조가 실무 문장 작성에 적합한가?
3. 신호 강도와 상품화 적합성을 별도로 보는 것이 유용한가? 실무에서는 어떤 표현이나 척도가 더 이해하기 쉬운가?
4. 근거의 최신성·독립성·출처 품질을 판단할 때 실제로 확인하는 기준은 무엇인가?
5. 반증, 미확인 항목, 불확실성을 화면에 표시한다면 어떤 수준이어야 신뢰를 높이고 부담은 줄일 수 있는가?
6. `진행/보류/종료`라는 상태명이 실제 회의·결재·업무 시스템에서 사용하는 말과 맞는가? 더 적합한 상태명이나 게이트가 있는가?
7. 후보를 상품 개발 검토로 넘길 때 반드시 필요한 검토자는 상품, 계리, 인수, 보상, 법무·준법, 채널 중 누구이며 시점은 언제인가?

### 3.3 기존 상품·약관 비교와 상품화 검토

1. 기존 상품이나 특약과 비교할 때 실제로 확인하는 문서와 항목은 무엇인가?
2. 화면에 상품명·보장 영역·면책·대상 고객·판매 상태·문서 버전 중 무엇을 우선 보여줘야 하는가?
3. `검색되지 않음`과 `보장되지 않음`을 구분하기 위해 실무자가 확인해야 할 절차는 무엇인가?
4. 상품화 가능성을 판단할 때 데이터 확보, 위험 측정, 가격, 인수, 보상, 재보험, 규제·소비자보호 중 어느 순서로 검토하는가?
5. 상품 가설 초안에 반드시 포함할 문장과, 초안 단계에서 보여주면 오해를 부르는 문장은 무엇인가?
6. 이 서비스가 실제 상품 결정을 대신하지 않으면서도 다음 조사 과제를 정하는 데 도움이 되려면 어떤 결과를 내야 하는가?

### 3.4 리포트와 협업

1. 리포트를 읽는 사람은 누구이며, 각 역할이 가장 먼저 확인하는 정보는 무엇인가?
2. 리포트 본문에 반드시 있어야 하는 내용과 부록으로 내려도 되는 내용을 나눠 달라.
3. 수치·문장·결론을 근거 ID로 되짚는 기능이 실제 검토에 얼마나 중요한가?
4. 의견·질문·결정 이력은 어떤 방식으로 남아야 하는가? 예: 댓글, 검토 항목, 승인 이력, 회의 기록 링크 등.
5. 리포트가 `진행`, `보류`, `종료` 결정을 요청할 때 필요한 책임자·기한·미결 질문은 무엇인가?
6. PDF·문서 내보내기가 필요한가? 필요하다면 수신자·권한·개인정보 검사를 어떤 방식으로 해야 하는가?

### 3.5 고객·영업 현장 신호의 활용

1. 개인 고객의 상황 입력에서 어떤 범주가 상품개발 조사에 유용하고, 어떤 입력은 오해·편향·재식별 위험이 큰가?
2. 고객이 상품을 찾는 과정에서 남긴 선택적 연구 동의를 어떤 별도 절차와 문구로 설명해야 신뢰할 수 있는가?
3. 고객 한 건이 아니라 여러 신호가 집계되었을 때, 실무자가 볼 수 있어야 하는 최소 단위는 무엇인가?
4. 영업부서 리포트에서 현장 담당자가 입력하기 쉬우면서도 검토 가능한 최소 필드는 무엇인가?
5. 영업부서의 관찰과 고객 원문·계약 정보·개별 보상 사례를 어떻게 구분해야 하는가?
6. 고객·영업 신호를 조사 우선순위의 보조 근거로 사용할 때 반드시 함께 봐야 하는 독립 근거는 무엇인가?

### 3.6 실제 도입 조건과 사용성

1. 이 도구를 주간·월간·특정 프로젝트 단위 중 어떤 업무 리듬에 넣는 것이 현실적인가?
2. 사내에서 사용하려면 SSO, 역할별 권한, 감사 로그, 문서 접근권한, 요청 ID 중 무엇이 첫 도입의 필수 조건인가?
3. 최신성은 어느 정도로 확인되어야 하는가? 데이터 기준 시각과 수집 실패를 어떤 위치에서 보여줘야 하는가?
4. 기존 문서·데이터·협업 도구와 어떤 방식으로 연결되어야 실제 사용이 늘어나는가?
5. 현업이 이 화면을 믿지 않게 되는 가장 큰 이유는 무엇이며, 화면이나 운영 절차로 어떻게 예방할 수 있는가?
6. 한 번의 파일럿에서 성공했다고 판단할 수 있는 실무 결과는 무엇인가? 예: 조사 시작 시간 단축, 중복 조사 감소, 근거 누락 감소, 의사결정 회의 준비 시간 단축 등.

## 4. 멘토에게 요청할 실무 피드백

### 4.1 가장 도움이 되는 피드백 형태

가능하면 아래 우선순위로 의견을 받고 싶다.

1. 실제 업무에서 반드시 필요한 항목
2. 있으면 좋지만 초기에는 없어도 되는 항목
3. 잘못 사용되거나 오해될 가능성이 있는 항목
4. 현재 용어와 맞지 않아 바꿔야 하는 항목
5. 운영 전에 다른 부서·시스템·규정 확인이 필요한 항목

### 4.2 익명화된 사례 1건에 대한 요청

공개 가능한 범위에서 특정 고객·계약·회사 기밀을 제외한 사례를 하나 골라 다음 질문에 답해 주시면 좋다.

```text
무엇이 시작 신호였는가?
처음 확인한 자료는 무엇이었는가?
누가 어떤 순서로 검토했는가?
후보가 되기 위해 부족했던 정보는 무엇이었는가?
진행/보류/종료를 가른 기준은 무엇이었는가?
최종적으로 남은 문서·결정·다음 과제는 무엇이었는가?
현재 과정에서 가장 큰 시간 손실 또는 반복 작업은 무엇이었는가?
```

사례를 제공하기 어렵다면 실제 자료 대신 단계명, 역할명, 필드명, 예상 소요 시간만 알려주셔도 충분하다.

### 4.3 화면을 보며 표시해 주실 항목

화면 시연 중 각 영역에 다음 중 하나를 표시해 주시면 우선순위 결정에 활용하겠다.

| 표시 | 질문 |
| --- | --- |
| 매일 필요 | 반복 업무에서 자주 확인하는가? |
| 결정에 필요 | 승인·보류·추가조사 판단에 직접 쓰이는가? |
| 참고 | 있으면 좋지만 다른 문서로 대체 가능한가? |
| 불필요 | 실제 업무에는 쓰이지 않는가? |
| 위험 | 오해·과잉 확신·개인정보 노출을 만들 수 있는가? |

## 5. 제공하지 않아도 되는 정보

멘토링을 위해 다음 정보는 요청하지 않는다.

- 고객 이름, 연락처, 주민등록번호, 상세 주소, 계약번호
- 고객 자유서술 원문이나 개인을 재식별할 수 있는 조합
- 공개되지 않은 상품·요율·인수 기준·보상 기준의 원문
- 회사 내부 시스템 계정, 인증정보, API 키
- 공개가 허용되지 않은 보고서·회의자료·거래처 정보

업무 적합성 확인에는 익명화된 구조, 필드, 역할, 의사결정 순서와 문제 유형만으로도 충분하다.
