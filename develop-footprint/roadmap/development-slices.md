# 개발 슬라이스와 통합 순서

각 슬라이스는 UI, 데이터 어댑터, 오류·빈 상태, 테스트, 문서를 함께 완료하는 세로 단위다. 여러 팀이 공통 파일을 동시에 재설계하지 않도록 도메인 계약을 먼저 합의한다.

## 0. 공통 기반 — 현재 완료

- 공통 셸과 안정 라우트
- 브랜드 토큰과 반응형 레이아웃
- 위험·근거·고객 신호 최소 계약
- 고객 인사이트 로컬 프로토타입
- 1~4 샘플 프레임

## 1. 근거 수집·출처 계보

소유: 데이터/플랫폼

- 승인 소스 레지스트리와 수집 상태
- 원문 URL, 발행·수집 시각, 중복군, 발췌, 데이터 사용권
- 채널별 실패·지연·재처리 상태
- 샘플과 실제 데이터를 명시적으로 분리하는 어댑터

1~4 모든 화면이 의존하므로 가장 먼저 통합한다. 수집기가 준비되지 않아도 고정 API 계약과 fixture로 UI 개발을 병행할 수 있다.

## 2. 후보 저장소와 목록

소유: 위험 후보 팀

- 후보 CRUD, 검색, 필터, 정렬, 저장 보기
- 상태·담당자·재검토일
- 중복 탐지와 병합 감사 기록
- `/risks` 샘플 교체

완료 후 대시보드와 상세가 같은 후보 ID를 사용해야 한다.

## 3A. 대시보드

소유: 탐지 대시보드 팀

- 채널 상태와 데이터 최신성
- 변화량·절대량·기준선 시각화
- 후보 우선 검토 큐
- 최소 집계된 고객 신호 큐
- 부분 실패와 빈 상태

후보 요약 API와 소스 상태 API에 의존한다. 2와 병렬 개발하되 fixture 필드 변경은 도메인 계약에 먼저 반영한다.

## 3B. 상세 평가

소유: 상품화 평가 팀

- 위험 정의와 근거 원장
- 반증·기존 상품 비교
- 분리된 평가 축과 의견 이력
- 진행/보류/종료 게이트
- `/risks/:riskId` 샘플 교체

후보 저장소와 근거 계보에 의존한다. 상품/약관 검색은 별도 승인 서비스 경계로 연결한다.

## 4. 리포트와 승인

소유: 리포트 팀

- 후보·근거·평가의 시점 스냅샷
- 미결 질문, 담당자, 기한
- 역할별 검토와 승인 이력
- 접근권한이 있는 내보내기
- `/reports` 샘플 교체

상세 평가 계약이 안정된 뒤 통합한다. 리포트 자체에 복제 데이터를 만들기보다 참조 ID와 스냅샷 버전을 보존한다.

## 5. 고객 인사이트 운영화

소유: 고객경험/데이터보호

- 승인 상품 마스터와 문서 검색
- 추천 설명·적합성 검토
- 공식 상담/가입 채널 인계
- 동의 원장, 서버 비식별화, 철회·삭제
- 집계 임계값과 실무자 검토 큐

고객 공개 채널이므로 1~4와 배포·인증을 분리한다. 집계된 신호 계약만 공유한다.

## 권장 병합 순서

```text
공통 계약
  → 근거 수집·후보 저장소
  → 목록
  → 대시보드 + 상세 평가
  → 리포트
  → 승인된 고객 신호 API 연동
```

## 각 팀 PR 체크리스트

- 담당 경로 밖 변경이 필요한 이유를 설명했는가?
- 샘플·실제 데이터 상태를 화면에서 구분했는가?
- 로딩·빈 상태·부분 실패·권한 없음이 정의됐는가?
- 모든 판단에서 근거와 시점을 추적할 수 있는가?
- 개인정보와 상품 확정 표현을 점검했는가?
- 모바일·키보드 사용을 확인했는가?
- `npm run check`가 통과하는가?
- `develop-footprint`의 현재 상태와 다음 의존성을 갱신했는가?
