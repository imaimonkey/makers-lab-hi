# 고객·영업 유입 기능 정리

이 문서는 현재 프로젝트에서 외부·현장 신호가 들어오는 두 경로를 하나의 기준으로 정리한다.

1. 영업부서의 현장 리포트·상품개발 제안
2. 개인고객의 생활 상황 검색과 선택적 연구 의견

두 경로 모두 현재는 발표·검증용 브라우저 동작이다. 운영 API나 실제 상품 판단으로 오해되지 않도록 `현재 구현`, `운영 전환 조건`, `실무자 연결 규칙`을 구분한다.

## 1. 한눈에 보는 유입 구조

| 구분 | 영업부서 유입 | 개인고객 유입 |
| --- | --- | --- |
| 사용자 | 현대해상 영업부서·현장 담당자 | 개인고객·가계 사용자 |
| 진입 경로 | `/sales-intake` | `/customer-insight` |
| 레이아웃 | `SalesLayout` 별도 모드 | `CustomerLayout` 별도 고객 웹 화면 |
| 입력 목적 | 현장 반복 문의, 산업·기술 변화, 상품개발 아이디어 접수 | 생활 상황에서 기존 상품 확인과 미충족 위험 탐색 |
| 핵심 처리 | 최소 글자 검증 후 접수 레코드 생성 | 규칙 기반 상품 후보 추천·신규 위험 키워드 탐지 |
| 저장 | `hi-risk-studio.sales-intake.v1`, 최대 30건 | `hi-risk-studio.customer-signals.v1`, 최대 20건 |
| 실무자 화면 연결 | 현재 자동 연결 없음. 접수 목록과 검토 대기 상태만 제공 | 동의한 비식별 연구 신호가 레이더 대시보드의 고객 인사이트 큐에 표시 |
| 운영 상태 | UI 구현·로컬 동작·접수 API 미연동 | UI 구현·로컬 동작·고객 인증/집계 API 미연동 |

## 2. 영업부서 유입

### 2.1 사용 흐름

```text
우상단 사용자 메뉴
  → 영업부서 모드
  → 현장 리포트·제안 입력
  → 브라우저 최소 검증
  → localStorage 접수
  → 최근 접수 목록·검토 대기 표시
  → (운영 전환 후) 접수 API·권한·중복 검토·실무자 후보 검토
```

영업부서 화면은 실무자 워크벤치와 유사한 테마를 사용하지만, 위험 후보를 직접 확정하는 화면이 아니다. `candidate-review`를 선택해도 현재 구현에서는 접수 레코드의 후속 희망 경로로만 남는다.

### 2.2 입력 계약

`SalesIntakeDraft`의 필드는 다음과 같다.

| 필드 | 현재 의미 | 검증·선택지 |
| --- | --- | --- |
| `type` | 입력 유형 | `field-report` 현장 리포트 / `product-proposal` 상품 개발 제안 |
| `channel` | 유입 채널 | 영업점·지점, 법인영업, GA·제휴, 고객 접점, 기타 |
| `subject` | 제안 제목 | 5자 이상, 최대 120자 |
| `observedRisk` | 현장에서 관찰한 위험·고객 반응 | 20자 이상, 최대 1,200자 |
| `proposal` | 상품화 방향 또는 추가 확인 내용 | 10자 이상, 최대 1,000자 |
| `followUp` | 원하는 다음 단계 | 신규위험 후보 검토, 상품개발 담당 연결, 근거 추가 확인, 우선 접수만 |

제출 시 제목·관찰 내용·제안 문장을 trim한 뒤 `SalesIntakeSubmission`을 만든다. 레코드에는 `id`, `submittedAt`, `status: received`가 추가된다.

### 2.3 현재 화면에서 확인되는 결과

- 접수 성공 시 접수 ID 앞 8자리와 접수 시각을 표시한다.
- 브라우저 저장에 실패하면 입력 내용을 임시 확인했다는 경고를 표시한다.
- 최근 접수는 현재 기기의 저장 목록에서 최대 4건을 보여준다.
- 저장 어댑터는 전체 목록을 최대 30건으로 자른다.
- 샘플 입력은 산업용 배터리 교체·재사용 과정의 책임 공백 사례다.

### 2.4 개인정보와 운영 경계

현재 화면은 고객 이름, 연락처, 계약번호, 상세 주소, 상담 원문을 입력하지 않도록 안내한다. 하지만 입력값을 서버에서 검사하거나 SSO·RBAC로 통제하는 운영 기능은 아직 없다.

운영 전환 시에는 다음을 추가해야 한다.

- `SalesIntakeSubmission` 서버 저장 및 요청 ID·감사 로그
- 영업부서·상품개발·검토자 권한 분리
- 동일 제안·반복 문의의 중복 및 최소 집계 기준
- 출처 문서·근거 ID 연결
- 사람의 검토를 통과한 경우에만 위험 후보 참조 ID 생성

## 3. 개인고객 생활 상황 유입

### 3.1 사용 흐름

```text
우상단 사용자 메뉴
  → 개인고객 모드
  → 생활 단계·생활 환경 선택
  → 걱정되는 상황 입력
  → 현재 필요한 도움 선택
  → (선택) 상품 연구 의견 활용 동의
  → 내 상황 분석
  → 기존 상품 후보·약관 확인 포인트·새로운 생활 위험 표시
  → (동의한 경우) 비식별 신호를 연구 큐에 저장
```

고객 화면은 보험 상품명을 먼저 검색하는 대신 가정·자동차·새 이동수단·AI·디지털 생활 등 상황을 입력하게 한다. 결과는 정보 탐색용 프로토타입이며 공식 가입설계, 보험료, 보장 확정, 인수 판단이 아니다.

### 3.2 입력 계약

`CustomerInsightInput`은 다음 값을 가진다.

| 필드 | 현재 의미 |
| --- | --- |
| `lifeStage` | 사회초년·1인 생활, 결혼·출산·자녀, 활동기·자산 형성, 중장년·가족 돌봄, 은퇴·건강 관리 |
| `contexts` | 주택·스마트홈, 자동차, 새 이동수단, 자녀 돌봄, 반려동물, 건강 관리, 여행·출장, 개인사업, AI·디지털 생활 |
| `situation` | 사용 제품·기술·환경과 예상 피해를 적는 자유 입력 |
| `concernLevel` | 미리 탐색, 기존 보험 빈틈 확인, 가까운 시일 내 상담 |
| `insightConsent` | 비식별 연구 신호를 실무자 큐에 보내는 선택 동의 |

개인정보 안내는 화면에 표시되며, 분석 전 `redactSensitiveText()`가 이메일·연락처·식별번호·일부 번호 형식을 치환하고 결과 문장을 최대 500자까지 제한한다. 원문은 현재 `localStorage`에 저장하지 않는다.

### 3.3 현재 분석 규칙

1. 사용자가 선택한 `contexts`와 상황 문장에서 키워드로 추론한 태그를 합친다.
2. 생활 단계별 보정 태그를 더해 상품 카탈로그의 태그와 일치하는 상품을 점수화한다.
3. 점수 순으로 최대 3개 상품 후보를 보여주고 관련도를 `높음·보통·탐색`으로 표시한다.
4. 상황 문장에서 다음 위험 테마의 키워드를 찾는다.

   - 생성형 AI·딥페이크 생활 피해
   - 분산에너지·배터리 생활 위험
   - 개인형·자율 이동수단 사고
   - 플랫폼·원격근무 경계 위험
   - 스마트홈·생활로봇 오작동
   - 웨어러블·디지털 헬스 의사결정 위험

5. 감지된 위험에는 `gapHypothesis`와 `analystQuestion`을 붙여 실무자 연구 질문으로 표현한다.

### 3.4 고객에게 보이는 결과

- 기존 상품 후보: 상품 요약, 추천 이유, 관련도, 약관 확인 포인트, 공식 상품 링크
- 신규 생활 위험: 위험 제목, 감지 키워드, 보장 공백 가설, 실무자 연구 질문
- 공식 상품 공시 링크: `productDisclosureUrl`
- 가입 가능 여부·보험료·보장 범위는 공식 상품설명서·약관·인수 심사 확인이 필요하다는 고지

동의하지 않은 경우에도 현재 화면에서 분석 결과는 볼 수 있지만, 신규 위험 카드의 연구 의견 전송 버튼은 비활성화된다.

## 4. 개인고객 신호의 실무자 환류

동의 후 고객이 신규 위험 카드의 연구 의견 보내기를 누르면 `buildCustomerSignal()`이 다음 구조를 만든다.

| 필드 | 저장 값 |
| --- | --- |
| `id`, `createdAt` | 브라우저 생성 ID와 ISO 시각 |
| `source` | `customer-voice` |
| `lifeStage` | 고객이 선택한 생활 단계 코드 |
| `theme`, `title` | 감지된 위험 테마와 제목 |
| `anonymizedSummary` | 마스킹된 상황 요약의 최대 180자 |
| `keywords` | 감지된 키워드 |
| `aggregationStatus` | 현재 항상 `sample-only` |
| `reviewStatus` | 현재 항상 `intake` |

저장 후 `hi-risk-studio:customer-signal` 브라우저 이벤트를 발생시킨다. 실무자 대시보드는 이 이벤트와 `storage` 이벤트를 듣고 고객 인사이트 유입 건수와 최대 3개의 요약을 갱신한다.

현재 환류는 다음 단계까지다.

```text
개인고객 동의
  → 비식별 CustomerSignal 생성
  → 같은 브라우저 localStorage 저장
  → 실무자 레이더의 고객 인사이트 큐 표시
```

아직 하지 않는 일:

- 단일 고객 신호를 위험 후보로 자동 승격
- 여러 고객 신호의 서버 집계·중복 제거
- 고객 원문·이름·연락처를 실무자 화면으로 전달
- 고객 신호를 상품 추천 또는 가입 판단의 근거로 확정

## 5. 두 유입 경로의 통합 기준

| 기준 | 영업부서 리포트 | 개인고객 신호 |
| --- | --- | --- |
| 원천의 성격 | 현장 담당자가 요약한 업무 맥락 | 고객이 입력한 생활 상황에서 추출한 연구 신호 |
| 원문 보관 | 현재 브라우저에 접수 내용 전체가 저장됨 | 원문은 저장하지 않고 마스킹 요약만 신호로 저장 |
| 검토 단위 | `SalesIntakeSubmission` | `CustomerSignal` |
| 현재 실무자 연결 | 자동 연결 없음 | 레이더 고객 인사이트 큐에 표시 |
| 후보 승격 | 자동 승격 없음 | 자동 승격 없음 |
| 운영 전환 필수 | API·SSO·RBAC·감사 로그·근거 ID | 고객 인증·동의 원장·집계·중복 제거·신호 API |

두 경로를 하나의 위험 후보로 합칠 때는 원천을 섞지 말고 `source`, `sourceId`, `receivedAt`, `evidenceIds`, `aggregationStatus`를 유지해야 한다. 상품개발 실무자의 판단은 반드시 근거 확인과 사람의 검토 단계를 거친다.

## 6. 발표·데모 시나리오

### 영업부서 유입

1. 사용자 메뉴에서 영업부서 모드 선택
2. `샘플 입력`으로 산업용 배터리 사례를 불러옴
3. `리포트 접수하기` 실행
4. 접수 ID·최근 접수 목록·검토 대기 상태 확인
5. 자동으로 위험 후보가 되지 않는다는 경계를 설명

### 개인고객 유입

1. 사용자 메뉴에서 개인고객 모드 선택
2. `예시 불러오기` 또는 생활 상황 직접 입력
3. 기존 상품 후보와 약관 확인 포인트 확인
4. 감지된 신규 생활 위험의 연구 질문 확인
5. 연구 의견 활용 동의 후 의견 보내기
6. 실무자 모드로 돌아가 레이더의 고객 인사이트 유입 건수와 요약 확인

## 7. 다음 개발 순서

1. 현재 브라우저 어댑터를 서버 어댑터로 교체하되 `SalesIntakeSubmission`·`CustomerSignal` 계약은 유지한다.
2. SSO·RBAC와 동의 버전·철회·감사 로그를 추가한다.
3. 최소 집계·중복 제거·출처·근거 ID를 적용한다.
4. 실무자 화면에 영업 접수와 고객 신호를 각각 원천 필터로 제공한다.
5. 검토자가 근거·불확실성·반증·보류 이유를 기록한 뒤에만 위험 후보로 연결한다.
6. 공식 상품·약관 카탈로그를 서버 기준으로 동기화하고 링크·개정 시각을 검증한다.
