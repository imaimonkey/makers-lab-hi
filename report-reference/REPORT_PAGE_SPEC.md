## 0. Codex 작업 지침

이 문서를 끝까지 읽고 현재 프로젝트의 구조와 사용 기술을 먼저 확인한 뒤 구현한다.

- 기존 프로젝트가 HTML/CSS/JavaScript이면 동일한 방식으로 구현한다.
- 기존 프로젝트가 React, Vite, Next.js 등이라면 해당 구조와 컴포넌트 방식을 따른다.
- 기존 공통 헤더, 내비게이션, 색상, 폰트, 레이아웃이 있다면 재사용한다.
- 핵심 기능 4가지 중 **4번째 리포트 페이지**만 구현한다.
- 새로운 상위 메뉴나 핵심 기능 탭을 추가하지 않는다.
- 다른 페이지와 공통 파일을 불필요하게 수정하지 않는다.
- 1차 구현에서는 외부 API를 연결하지 않고 가상데이터를 사용한다.
- UI에 표시되는 AI 결과는 반드시 `AI 생성 초안`임을 명시한다.
- 실제 보험상품 출시 결정, 보험료 산출, 최종 약관 확정 기능처럼 표현하지 않는다.
- 구현이 끝나면 수정·생성한 파일 목록과 실행 방법을 설명한다.

## 1. 프로젝트 배경

현대해상 일반상품개발 실무자는 사회·산업 변화에서 발생하는 신규 위험을 조사하고, 해당 위험이 보험상품으로 개발 가능한지 검토한다.

현재 신규 위험 관련 정보는 뉴스, 공공통계, 법령·규제, 기업공시, 판례, 분쟁사례 등 여러 채널에 흩어져 있다. 또한 실무자는 수집한 위험이 실제 보험상품으로 적합한지 판단하기 위해 시장성, 보험성, 보장 공백, 책임주체, 데이터 확보 가능성, 약관 명확성 등을 별도로 검토해야 한다.

본 서비스는 외부 데이터를 기반으로 신규 위험 후보를 탐지하고, 근거자료와 함께 상품화 가능성을 1차 분석하여 보험상품 개발 담당자의 의사결정을 지원하는 서비스다.

AI는 최종 결정을 내리지 않는다. AI는 자료 조사와 1차 검토를 지원하고, 최종 판단은 실무자가 수행한다.

## 2. 전체 서비스의 핵심 기능 4가지

1. **대시보드**  
   신규 위험 현황과 우선 검토 대상을 종합적으로 확인한다.

2. **위험 탐색**  
   탐지된 신규 위험 후보를 표와 필터로 탐색한다.

3. **위험 상세**  
   특정 위험이 왜 위험으로 탐지되었는지 평가 기준과 근거자료를 확인한다.

4. **리포트**  
   선택한 신규 위험의 보험상품화 가능성, 보험 대상, 상품 방향, 약관화 가능성 등을 종합적으로 검토한다.

### 리포트 페이지의 역할

리포트 페이지는 위험 상세 내용을 반복해서 보여주는 페이지가 아니다. 다음 질문에 답하는 최종 의사결정 지원 화면이다.

> 이 위험을 보험으로 만들 수 있는가?  
> 누구를 보험 대상으로 해야 하는가?  
> 어떤 상품 구조가 적합한가?  
> 약관으로 명확하게 표현할 수 있는가?  
> 상품화 전에 무엇을 추가로 조사해야 하는가?

## 3. 이번 프로토타입의 목표

### 3.1 구현 목표

- `전기차 지하주차장 화재 위험`을 시연 주제로 한 리포트 화면을 구현한다.
- 사용자가 리포트 생성 버튼을 누르면 AI가 분석하는 것처럼 로딩 상태를 보여준다.
- 로딩이 끝나면 가상데이터 기반의 종합 리포트를 표시한다.
- 실무자가 판단 근거와 부족한 정보를 확인할 수 있게 한다.
- 실무자가 검토 상태와 메모를 남길 수 있게 한다.
- 발표 시 실제 업무용 서비스처럼 전체 흐름을 시연할 수 있게 한다.

### 3.1.1 시연 시나리오

이번 프로토타입은 실제 출시 사례를 활용한 **과거 시점 재구성형 검증**으로 시연한다.

- 분석 기준시점: `2026.02.28`
- 가정: 해당 시점에 전기차 화재 관련 위험 신호와 기존 보험의 보장 공백이 탐지된 상황
- AI 입력: 위험 신호, 피해 유형, 이해관계자, 기존 자동차·화재·배상책임보험의 보장 가능 영역과 공백, 일반 화재보험 약관 구조
- AI 입력에서 제외: 실제 출시된 전기차화재안심보험의 최종 결론과 완성된 약관 문구
- 사후 검증: AI 결과를 실제 전기차화재안심보험의 상품 구조·사업방법서와 비교

발표 문구 예시:

> 실제로 최근 보험상품화된 신규 위험 사례를 과거 시점 기준으로 재구성하여, AI가 실제 상품과 유사한 방향을 도출할 수 있는지 검증했습니다.

화면의 모든 분석 수치와 결론에는 `프로토타입용 가상데이터` 또는 `AI 생성 초안` 표시를 붙인다.

### 3.2 이번 구현 범위

- 리포트 생성 전 화면
- AI 분석 중 로딩 화면
- 리포트 생성 완료 화면
- AI 1차 검토 결론
- 위험 및 기존 보장 공백 요약
- 보험 대상 적합성
- 상품화 가능성 평가
- 추천 상품 구성안
- 약관화 가능성 및 검토용 문구 제안
- 근거자료 및 추가 조사 필요사항
- 실제 출시상품과의 사후 검증 비교 모달
- 실무자 검토 상태 및 메모
- 인쇄 또는 PDF 저장 기능

### 3.3 이번에 구현하지 않는 범위

- 대시보드, 위험 탐색, 위험 상세 페이지 신규 제작
- 실제 뉴스·통계·법령 API 연결
- 실제 보험료 계산
- 실제 위험률 또는 요율 산출
- AI의 최종 상품 출시 결정
- 법적 효력이 있는 최종 보험약관 작성
- AI 결과 본문 직접 편집 및 버전관리
- 모든 약관 PDF를 검색하는 완전한 RAG 시스템
- 사용자 인증, 권한관리, 데이터베이스 저장

## 4. 페이지 진입 및 상태

새로운 상위 탭을 추가하지 않고 기존 4번째 `리포트` 메뉴 안에서 모든 상태를 처리한다.

### 4.1 생성 전 상태

- 페이지 제목: `신규 위험 상품화 검토 리포트`
- 안내 문구: `검토할 신규 위험을 선택하면 AI가 상품화 가능성과 약관화 가능성을 분석합니다.`
- 위험 선택 드롭다운
- 기본 선택값: `전기차 지하주차장 주차·충전 중 화재`
- 주요 위험 정보 미리보기
- `리포트 생성` 버튼
- 기존 리포트 목록은 별도 탭이 아니라 같은 페이지의 작은 드롭다운 또는 선택 영역으로만 표현할 수 있다.

### 4.2 AI 분석 중 상태

리포트 생성 버튼을 누르면 약 1.5~2.5초 동안 로딩 화면을 표시한다.

로딩 문구 예시:

1. 위험 및 보장 공백을 확인하고 있습니다.
2. 보험 대상과 상품 방향을 검토하고 있습니다.
3. 기존 약관과 유사 보장을 비교하고 있습니다.
4. 검토용 리포트를 생성하고 있습니다.

진행바 또는 단계별 체크 표시를 사용할 수 있다.

### 4.3 생성 완료 상태

- 생성 전 선택 영역은 축소한다.
- 전체 리포트를 표시한다.
- 상단에 `AI 생성 초안` 배지를 표시한다.
- 화면 하단 또는 우측에 실무자 검토 영역을 표시한다.

### 6.2 AI 1차 검토 결론

상단에 5개의 요약 카드를 배치한다.

| 카드 | 결과 | 보조 설명 |
|---|---|---|
| 검토 우선순위 | 우선 검토 | 대형 집적손해 가능성과 보장 공백이 확인됨 |
| 추천 보험 대상 | 혼합형 | 기업·기관이 계약하고 차량 소유자와 제3자를 보호하는 구조 검토 |
| 추천 상품 방향 | 보완보험 | 기존 자동차·화재보험 우선 보상 후 공백·초과손해 보완 |
| 약관화 가능성 | 조건부 가능 | 사고와 손해는 정의 가능하나 보상 순서·발화 기준 확정 필요 |
| 데이터·요율 준비도 | 보완 필요 | 사고 빈도, 집적손해 및 최대손실 자료 부족 |

카드 클릭 또는 `판단 근거 보기` 버튼을 누르면 짧은 근거 설명을 펼쳐 보여준다.

AI 종합 의견 예시:

> 전기차가 지하주차장에서 주차 또는 충전 중 화재를 일으킬 경우 주변 차량과 건물에 대규모 재산손해가 확산될 수 있습니다. 기존 자동차보험·화재보험에서 일부 손해를 보상할 수 있으나, 발화 원인과 책임 확정이 지연되거나 다수 피해가 발생하면 보상 순서와 한도에 공백이 생길 가능성이 있습니다. 기업·기관이 계약 주체가 되고 보장대상 전기차와 제3자 재산손해를 연결하는 보완보험 구조를 우선 검토할 수 있습니다. 다만 발화 차량의 판정 기준, 기존 보험과의 중복 처리, 집적손해 규모와 요율 자료를 추가로 확인해야 합니다.

AI 결과를 확정적 사실처럼 표시하지 않는다. `예상`, `검토 필요`, `조건부`, `근거 부족` 등의 표현을 사용한다.

### 6.3 위험 및 기존 보장 공백 요약

위험 상세 페이지와 중복되지 않도록 핵심 내용만 요약한다.

표시 항목:

- 위험 한 줄 정의
- 왜 지금 검토해야 하는지
- 주요 피해 유형
- 영향을 받는 대상
- 기존 보험의 보장 가능 영역
- 기존 보험으로 설명하기 어려운 공백

가상데이터:

**위험 정의**  
전기차가 지하주차장 등에서 주차 또는 충전 중 화재를 일으켜 주변 차량과 건물에 대규모 제3자 재산손해를 발생시키는 위험

**왜 지금 검토해야 하는가**

- 전기차 보급과 지하주차장 내 충전·주차가 확대되고 있음
- 밀폐된 공간에서 화재가 발생하면 연소 확대와 진압 지연으로 다수 차량·건물 설비에 손해가 확산될 수 있음
- 배터리, 충전설비, 차량 결함, 외부 요인 등 발화 원인 규명에 시간이 걸릴 수 있음
- 원인과 법률상 책임이 확정되기 전 피해자가 보상을 기다리는 공백이 발생할 수 있음

**주요 피해 유형**

- 인접 차량의 소손·그을음·열 손해
- 주차장 벽체, 전기설비, 소방설비 등 건물·시설 손해
- 연기·소화수에 의한 추가 재산손해
- 대피·복구 과정의 사용 제한과 영업중단 등 간접손해 후보

**기존 보험과의 관계**

- 발화 차량의 자동차보험 대물배상과 일부 중복 가능
- 피해 차량의 자기차량손해 담보와 일부 중복 가능
- 건물·시설 손해는 화재보험 또는 재산종합보험과 일부 중복 가능
- 차량·배터리 결함이 확인되면 생산물배상책임보험과 연계될 수 있음

**보장 공백**

- 발화 원인 또는 책임주체가 확정되기 전 보상이 지연될 수 있음
- 동일 장소의 다수 차량과 건물이 함께 피해를 입으면 기존 보상한도를 초과할 수 있음
- 자동차보험·화재보험·생산물배상책임보험 사이의 보상 순서와 구상관계가 복잡할 수 있음
- 원인 미상 화재, 발화 차량 자체 손해, 신체손해, 영업중단손해의 포함 여부를 구분해야 함

### 6.4 보험 대상 적합성

개인보험, 기업보험, 혼합형 중 어디에 더 적합한지를 보여준다.

| 대상 | 적합성 | 판단 이유 |
|---|---|---|
| 기업보험 | 적합 | 제조·수입사, 협회 또는 기관을 계약 주체로 하면 위험을 집단 단위로 관리할 수 있음 |
| 개인보험 | 부분 적합 | 개인 전기차 소유자도 보장과 연결되지만 개별 가입만으로는 피해자 신속 보상과 역선택 관리에 한계가 있을 수 있음 |
| 혼합형 | 추천 | 기업·기관이 단체계약을 체결하고 보장대상 차량과 제3자 피해를 연결하는 구조가 목적에 가장 부합함 |

관계자 구조:

- 예상 보험계약자: 전기차 제조·수입사, 관련 협회 또는 정책 수행기관 중 검토
- 예상 피보험자: 보험증권 또는 대상 차량 명부에 기재된 전기차 소유자·사용자 중 구조에 따라 확정
- 주요 피해자: 인접 차량 소유자, 건물·주차장 소유자 또는 관리주체 등 제3자
- 위험관리 주체: 제조·수입사, 차량 소유자, 충전시설 운영자, 주차장 관리주체
- 추가 책임 검토 대상: 배터리 제조사, 충전사업자, 시설 소유·관리자
- 보험료 부담 주체: 제조·수입사 중심, 공공 지원 또는 공동부담 가능성 별도 검토

`보험계약자`, `피보험자`, `보험수익자`, `피해자`를 같은 의미로 표시하지 않는다. 실제 상품 구조 확정 전에는 각 역할을 `검토안`으로 표시한다.

점수만 표시하지 말고 반드시 판단 이유를 함께 보여준다.

### 6.6 추천 상품 구성안

표시 항목:

- 가칭 상품명
- 추천 상품 형태
- 예상 보험 대상
- 보험의 목적 또는 보장 대상
- 보장 사고
- 보장 손해
- 기존 상품과의 관계
- 보험기간 방향
- 보상한도·자기부담금 검토 방향
- 추천 이유

가상데이터:

- 가칭 상품명: `전기차 화재 제3자 재산손해 보완보험`
- 추천 형태: `기업·기관 단체계약 또는 정책연계형 보완보험 우선 검토`
- 보험 대상: `보험증권 또는 대상 차량 명부에 기재된 전기자동차`
- 기본 보장: `보장대상 전기차가 주차 또는 충전 중 일으킨 화재로 발생한 제3자의 차량·건물 등 직접 재산손해`
- 기존 상품 관계: `자동차보험·화재보험 등 기존 보험의 우선 보상 후 남는 공백 또는 약정한 초과손해 보완 검토`
- 보험기간: `단체계약 1년 및 대상 차량의 보장기간 연계 검토`
- 보상한도: `지하주차장 최대예상손실과 기존 보험 한도를 바탕으로 별도 산정 필요`
- 자기부담금: `피해자 신속 보상 목적과 소액손해 관리의 균형을 고려해 적용 여부 검토`

AI가 실제 보험료, 보상한도, 자기부담금 수치를 확정해서는 안 된다. 방향과 추가 검토 필요성을 제시한다.

### 6.7 약관화 가능성 및 검토용 문구 제안

이 영역은 리포트 페이지의 핵심 차별화 기능이다.

영역 제목 아래에 다음 안내를 표시한다.

> 기존 약관과 수집된 근거를 바탕으로 AI가 생성한 검토용 초안입니다. 최종 약관 확정을 위해 상품·법무·계리 담당자의 검토가 필요합니다.

#### 6.7.1 약관화 가능성

- 결과: `조건부 가능`
- 가능 사유: 보장대상 전기차, 주차·충전 중 화재, 제3자 직접 재산손해의 기본 구조를 정의할 수 있음
- 보완 사유: 발화 차량의 판정 기준, 원인 미상 사고의 처리, 기존 보험의 우선 보상과 중복보험 처리 순서를 추가로 정의해야 함

약관화 가능성 판단 기준:

1. 보험계약자와 피보험자를 식별할 수 있는가?
2. 보험의 목적 또는 보장 대상을 구체화할 수 있는가?
3. 보험사고를 객관적으로 정의할 수 있는가?
4. 보험금 지급조건을 확인 가능한 형태로 작성할 수 있는가?
5. 보상하지 않는 상황을 구체적으로 정할 수 있는가?
6. 사고 원인과 책임주체를 구분할 수 있는가?
7. 기존 상품과 중복되는 보장을 구분할 수 있는가?

#### 6.7.2 추천 보장 문구 초안

> 회사는 보험증권 또는 대상 차량 명부에 기재된 보장대상 전기자동차가 보험기간 중 주차 또는 충전 중 발생한 화재로 제3자의 자동차 또는 건물 등 재물에 직접적인 손해를 입힌 경우, 약관에서 정한 기존 보험의 보상 적용 후 남은 손해를 보상한도 내에서 보상합니다.

이 문구는 설명용 초안이다. 실제 약관 작성 시 다음 두 구조 중 하나를 먼저 확정해야 한다.

- `배상책임형`: 피보험자의 법률상 손해배상책임이 확정된 경우 보상
- `피해보완형`: 책임 확정 전이라도 객관적인 사고·손해 요건을 충족하면 제3자 재산손해를 우선 보상하고 이후 구상관계를 정산

본 시연에서는 피해자 신속 보상과 원인 규명 지연 문제를 보여주기 위해 `피해보완형 검토안`을 우선 제시한다.

문구는 편집 불가능한 읽기 전용 카드로 표시한다. `문구 복사` 버튼은 제공할 수 있다.

#### 6.7.3 핵심 용어 정의 후보

- 보장대상 전기자동차
- 주차 중
- 충전 중
- 화재
- 발화 차량
- 원인 미상 화재
- 제3자
- 재물손해
- 직접손해
- 기존 보험
- 하나의 사고

각 용어 옆에 `정의 필요`, `기존 약관 참고 가능`, `추가 검토 필요` 등의 상태를 표시한다.

#### 6.7.4 보험금 지급조건 초안

- 보험기간 중 사고가 발생했을 것
- 보험증권 또는 대상 차량 명부에 기재된 전기차와 관련된 사고일 것
- 약관에서 정한 주차 또는 충전 상태에서 발생한 화재일 것
- 관계기관의 조사자료 등으로 보장대상 차량에서 시작된 화재임이 합리적으로 확인될 것
- 제3자의 차량 또는 건물 등 재산에 발생한 직접손해가 객관적으로 확인될 것
- 자동차보험·화재보험 등 기존 보험의 적용 여부와 보상액이 확인될 것
- 동일한 손해에 대한 중복 보상을 제외할 수 있을 것
- 약관에서 정한 사고 통지 및 청구 절차를 이행할 것

`발화 원인이 완전히 확정되어야 하는지`와 `합리적인 개연성만으로 인정할 수 있는지`는 실무·법무 검토가 필요한 핵심 쟁점으로 강조한다.

#### 6.7.5 면책사항 검토 후보

- 계약자 또는 피보험자의 고의
- 보장대상 차량의 불법 개조 또는 배터리·충전장치의 임의 변경으로 발생한 사고
- 주행 중 발생한 사고. 단, 별도 담보로 정한 경우 제외
- 보장대상 전기차 자체의 손해
- 제3자의 신체 상해. 단, 별도 담보로 정한 경우 제외
- 약관에서 정한 기존 보험으로 전액 보상된 손해
- 영업중단, 사용손실 등 간접손해. 단, 별도 담보로 정한 경우 제외
- 대상 차량 명부에 포함되지 않은 차량에서 시작된 화재
- 충전시설 또는 건물 자체의 결함만으로 발생한 사고
- 전쟁, 테러 등 일반적인 면책사유

면책사항은 확정안이 아니라 `검토 후보`로 표시한다.

#### 6.7.6 모호성 및 추가 검토

- `주차 중`에 입·출차를 위한 저속 이동이나 시동 상태를 포함할지
- 완속·급속·비접촉 충전 중 어디까지 `충전 중`으로 볼지
- 발화 차량이 완전히 소실되어 원인이 확정되지 않는 경우 인정 기준을 어떻게 정할지
- 자동차보험, 피해 차량의 자차보험, 건물 화재보험 중 어떤 보험을 우선 적용할지
- 다수 피해가 하나의 화재에서 발생한 경우 `하나의 사고`와 총보상한도를 어떻게 정의할지
- 발화 차량 자체 손해, 신체손해, 소화활동 비용, 영업중단손해를 포함할지
- 손해를 먼저 보상한 뒤 제조사·충전사업자·시설 관리자에게 구상하는 절차를 어떻게 정할지

- 사업장화재보험: 건물·시설 화재손해, 배상책임 및 특별약관 구조 참고
- 주택화재보험: 개인 소유 재산과 화재 배상책임의 보장 구조 참고
- 전기차화재안심보험: AI 결과의 상품 대상·보장 사고·보상 순서 방향성을 사후 검증

`원문 보기`는 프로토타입용 상세 모달을 열어 자료명, 참고 이유, 주요 확인 항목을 보여준다. 실제 파일 링크가 없으면 존재하지 않는 URL을 만들지 않는다.

### 6.8 근거자료 및 추가 조사 필요사항

#### 근거자료 목록

각 근거자료는 다음 필드를 가진다.

- 자료 유형
- 자료명
- 출처
- 기준일 또는 작성일
- 어떤 판단에 사용했는지
- 근거 신뢰도
- 원문 링크 또는 `프로토타입용 가상자료` 표시

자료 유형 예시:

- 공공통계
- 법령·규제
- 판례·분쟁사례
- 기업공시
- 보험약관
- 전문기관 보고서
- 뉴스

가상 근거자료는 실제 자료처럼 오해되지 않게 `프로토타입용 가상자료` 배지를 표시한다.

#### 근거의 사용 원칙

- 뉴스는 신규 위험 발견 신호로 사용한다.
- 상품화 판단은 공공통계, 법령, 공시, 판례, 분쟁사례, 실제 약관 등 더 강한 근거를 우선한다.
- 근거가 부족하면 AI가 임의로 확정하지 않고 `근거 부족` 또는 `판단 보류`로 표시한다.
- 각 주요 결론에서 어떤 자료를 사용했는지 확인할 수 있어야 한다.

#### 추가 조사 필요사항

- 국내 전기차 화재 건수와 주차·충전 상태별 발생 비중
- 지상·지하주차장별 평균 재산손해액과 최대 집적손해 사례
- 발화 원인 미상으로 종결된 사고의 비율과 판정 기준
- 인접 차량, 건물, 충전설비별 손해액 분포
- 자동차보험·자차보험·화재보험·생산물배상책임보험의 실제 보상 사례
- 차량 소유자, 제조사, 충전사업자, 주차장 관리자의 책임이 문제된 판례 또는 분쟁사례
- 하나의 화재에서 발생 가능한 최대예상손실과 재보험 필요성
- 전기차·배터리·충전시설 관련 화재안전기준과 제도 변화
- 보험료 산출에 필요한 위험률 자료

실무 검토 상태 옵션:

- 미검토
- 검토 중
- 추가 조사 필요
- 1차 검토 완료

추가 조사 체크리스트:

- 요율 산출 가능성 검토
- 관련 법령·규제 확인

실무자 메모 예시:

## 7. 레이아웃 및 디자인 방향

### 7.1 전체 인상

- 보험회사 내부 업무 시스템에 어울리는 신뢰감 있고 차분한 디자인
- 화려한 소비자용 서비스보다 B2B 의사결정 지원 도구의 느낌
- 한 화면에 정보를 과도하게 압축하지 않고 섹션별 카드로 구분
- 결론을 먼저 보여주고 아래로 내려갈수록 상세 근거가 나타나는 구조

### 7.2 권장 색상

기존 팀 디자인 시스템이 있으면 기존 색상을 우선한다. 별도 디자인이 없다면 다음을 사용한다.

- Primary Navy: `#123B6D`
- Primary Blue: `#2563EB`
- Accent Orange: `#F59E0B`
- Success Green: `#15803D`
- Warning Orange: `#D97706`
- Danger Red: `#B91C1C`
- Background: `#F5F7FA`
- Card: `#FFFFFF`
- Text Main: `#1F2937`
- Text Sub: `#6B7280`
- Border: `#E5E7EB`

### 7.3 화면 배치

- 최대 콘텐츠 너비: 약 `1280px~1440px`
- 상단: 헤더와 AI 핵심 결론 카드
- 중단: 위험 요약, 대상 적합성, 상품화 평가, 추천 구성안
- 하단: 약관화 가능성, 근거자료, 실무자 검토
- 데스크톱에서는 2열 카드 배치를 일부 사용할 수 있다.
- 모바일 또는 좁은 화면에서는 1열로 전환한다.
- 상태는 색상만으로 구분하지 말고 텍스트 라벨을 함께 표시한다.

### 7.4 컴포넌트

- KPI 요약 카드
- 정보 카드
- 평가 테이블
- 아코디언 또는 상세 펼침 영역
- 근거자료 카드
- 모달
- 체크리스트
- 메모 입력창
- 로딩 진행바
- 인쇄 버튼

## 8. 인터랙션 명세

1. `리포트 생성` 클릭
   - 생성 전 화면을 로딩 화면으로 변경한다.
   - 단계별 분석 문구를 순차적으로 표시한다.
   - 약 1.5~2.5초 후 리포트 결과를 표시한다.

2. `판단 근거 보기` 클릭
   - 해당 카드 아래에 판단 이유와 사용 근거를 펼친다.

3. 상품화 평가 행 클릭
   - 판단 근거, 사용 자료, 추가 확인사항을 펼친다.

4. `원문 보기` 클릭
   - 출처 상세 모달을 표시한다.
   - 가상자료라면 가상자료임을 분명히 표시한다.

5. `실제 상품과 비교` 클릭
   - AI 결과와 사후 검증자료의 공통점·차이점을 모달로 표시한다.
   - 본 비교는 데모의 검증 과정이며 AI의 최초 입력에는 실제 상품 결론을 사용하지 않았음을 표시한다.

6. `문구 복사` 클릭
   - 추천 보장 문구를 클립보드에 복사한다.
   - 짧은 완료 토스트를 표시한다.

7. 실무 검토 상태 변경
   - 선택한 상태를 화면에 반영한다.
   - localStorage에 저장한다.

8. 검토 메모 저장
   - localStorage에 저장한다.
   - 새로고침 후에도 유지한다.

9. `인쇄/PDF 저장` 클릭
   - 브라우저 인쇄 기능을 실행한다.
   - 인쇄 시 버튼, 입력창, 불필요한 UI를 숨긴다.

## 9. 가상데이터 관리 원칙

- 화면에 직접 텍스트를 반복해서 하드코딩하지 않는다.
- 리포트 데이터는 별도 객체 또는 파일에서 관리한다.
- Vanilla JavaScript 프로젝트라면 `mock-data.js` 사용을 권장한다.
- 로컬 파일 실행 시 JSON fetch 오류를 피하기 위해 단순 프로토타입에서는 JS 객체 방식이 적합하다.

권장 데이터 구조 예시:

```js
const mockReport = {
  meta: {
    analysisMode: "retrospective-benchmark",
    analysisBaseDate: "2026-02-28",
    isMockData: true
  },
  aiSummary: {},
  riskGapSummary: {},
  targetSuitability: [],
  productFeasibility: [],
  productProposal: {},
  wordingFeasibility: {},
  evidence: [],
  missingResearch: [],
  validationComparison: {
    excludedFromAiInput: true,
    similarities: [],
    differences: []
  },
  reviewer: {}
};
```

화면 컴포넌트는 위 데이터 객체를 기반으로 렌더링한다.

- 모바일에서 표가 잘리지 않도록 카드 전환 또는 가로 스크롤을 제공한다.
- 브라우저 콘솔에 오류가 없어야 한다.
- 빈 데이터나 오류 상태에서도 화면이 무너지지 않아야 한다.

## 11. 향후 포텐스닷 API 연결 계획 - 이번 구현 제외

1차 프로토타입은 가상데이터로 구현한다. 이후 포텐스닷 API는 전체 리포트보다 다음 기능에 우선 연결한다.

> `약관 검토용 문구 다시 제안받기`

### 11.1 입력 정보

- 신규 위험명
- 예상 보험 대상
- 보장 사고
- 보장 손해
- 책임주체
- 기존 보험의 보장 가능 영역과 공백
- 기존 보험의 우선 보상 또는 중복 처리 조건
- 사용자가 선택한 기존 약관 참고문구

### 11.2 기대 출력 구조

```json
{
  "feasibilityStatus": "조건부 가능",
  "coverageDraft": "검토용 보장 문구",
  "definitions": ["정의가 필요한 용어"],
  "paymentConditions": ["보험금 지급조건"],
  "exclusionCandidates": ["면책 검토 후보"],
  "ambiguities": ["추가 검토가 필요한 모호성"],
  "disclaimer": "AI가 생성한 검토용 초안"
}
```

### 11.3 보안 원칙

- 포텐스닷 API 키를 HTML 또는 프론트엔드 JavaScript에 직접 작성하지 않는다.
- 브라우저에서 포텐스닷 API를 직접 호출하지 않는다.
- GAS, Node.js 등 중간 서버를 통해 호출한다.
- API 키는 GAS 스크립트 속성 또는 서버 환경변수에 저장한다.
- `.env` 파일을 사용할 경우 `.gitignore`에 포함한다.
- API 실패 시 기존 가상데이터 결과를 보여주는 fallback을 제공한다.

### 11.4 참고자료 사용 방식

- PDF 전체를 매번 프롬프트에 넣지 않는다.
- 신규 위험과 관련된 약관 문구만 선별해 참고문구로 전달한다.
- AI가 어떤 기존 약관을 참고했는지 결과 화면에 표시한다.
- 향후 데이터가 충분해지면 약관 검색 기능 또는 RAG 구조를 별도 확장안으로 검토한다.
